# TicketRush: новая модель и CreateEvent

Подробный [разбор каждой сущности, файлов и пути запроса](project-walkthrough.md) — в отдельном документе.

## Что согласовано

Продукт — покупка билетов на мероприятия без нумерованных мест. Ядро — модульный монолит, фоновые задачи — отдельные workers из того же проекта. Самостоятельный микросервис отличается тем, что владеет своей бизнес-областью и контрактом; отдельный процесс ещё не делает worker микросервисом.

Пока работаем через Postman. Интерфейс по готовым пользовательским сценариям реализует ассистент; разработка frontend не является заданием для автора Go-кода.

## Деньги

Используем github.com/shopspring/decimal v1.4.0. Amount — рубли, а не копейки. В PostgreSQL — NUMERIC(18,2), в JSON — строка. Пример: `{"amount":"1299.90","currency":"RUB"}`. Сериализация decimal может убрать незначащие нули: `1299.9` имеет ту же стоимость.

Создавай через `domain.NewMoney("1299.90", domain.CurrencyRUB)`. Не преобразуй цену через float64. Отрицательные значения, дробная копейка и сумма вне диапазона отклоняются. Нулевая цена допустима для бесплатного тарифа. Изменение цены не изменяет уже оформленные BookingItem/Order.

## Текущая ручка

```http
POST /api/v1/organizer/events
Content-Type: application/json

{
  "name": "Go Live",
  "description": "Конференция о Go",
  "category": "conference"
}
```

Ответ — 201 Created с Location, application/json и X-Request-Id:

```json
{
  "id": "...",
  "organizer_id": "...",
  "name": "Go Live",
  "description": "Конференция о Go",
  "category": "conference",
  "status": "draft",
  "created_at": "...",
  "updated_at": "..."
}
```

OrganizerID и UserID берутся из серверной identity. Передать organizer_id, status, total_tickets или created_at в теле нельзя. Название очищается по краям и содержит 1–200 символов, описание — до 10000, категория — до 100. Описание и категория пока необязательны для черновика. Время создания возвращает PostgreSQL. При публикации будут отдельные проверки полноты карточки и сеансов.

HTTP DTO лежат в transport; CreateEventInput — в service. Сервис создаёт и валидирует domain.Event, репозиторий проверяет членство организатора и вставляет событие одним SQL-запросом. Ответ преобразуется в EventResponse. Ошибка SQL не попадает в тело HTTP.

Коды: 400 — некорректное тело/поля, 401 — нет identity, 403 — нет роли или членства, 413 — тело больше 1 MiB, 415 — неподходящий Content-Type, 500 — внутренняя ошибка. В теле ошибки есть code, message, request_id. Причины ошибок валидации пока подробно видны в локальных логах; формат ошибок отдельных полей расширим позже.

GET /api/v1/organizer/events/{id} и остальные CRUD ещё не написаны: это следующая задача. В кабинете организатор получает свои черновики; публичная GET /api/v1/events/{id} впоследствии показывает только published. Значение Location уже указывает на будущую ручку получения карточки. Старые маршруты бронирования в памяти не зарегистрированы в основном приложении. Учебные handlers и их тесты сохранены в internal/legacy/bookingdemo с собственной старой моделью.

## Запуск для Postman

1. Если .env ещё нет, создай его из .env.example. Для существующего файла добавь отсутствующие настройки, не заменяя свой конфиг.
2. Выполни `make seed`: он проверит начальную схему, применит миграции и добавит dev-данные.
3. В .env установи:

```dotenv
LOGGER_LEVEL=DEBUG
LOGGER_FOLDER=logs
HTTP_ADDR=127.0.0.1:8080
DEV_AUTH_ENABLED=true
DEV_USER_ID=22222222-2222-4222-8222-222222222222
DEV_ORGANIZER_ID=33333333-3333-4333-8333-333333333333
```

4. Запусти `make run`. Эта команда повторно проверяет миграции и seed и запускает сервер только после их успешного завершения. Отправь запрос выше в Postman.

DEV_AUTH_ENABLED по умолчанию false. Это временная локальная identity, а не JWT. При включении сервер разрешает только loopback-адрес и использует заданные сервером UUID. Роль из cookie/заголовка игнорируется. Без dev identity и до подключения настоящей авторизации создание отвечает 401. Seed создаёт пользователя, организатора и членство с этими UUID.

## Миграция 003

Добавляет users, organizers, organizer_memberships, venues, sessions, ticket_types и поля новой карточки Event. Старые события сохраняются как draft специального legacy-организатора. Старые остатки и bookings сохраняются в БД, но API новой модели их не использует. Не создаём фиктивную дату, площадку и цену для старых событий.

У старых total_tickets/available_tickets снимается NOT NULL, чтобы новые карточки создавались без остатков. После переноса исторических данных в сеансы и тарифы уберём эти столбцы отдельной миграцией. Уже применённые 001 и 002 не изменены.

Откат 003 откажет, если уже созданы карточки без старых остатков: он не будет придумывать для них количество билетов. Проверяй данные и делай backup перед таким откатом.

7 октября 2026 начальная схема локальной dev-базы проверена и согласована с журналом migrate; миграции 002 и 003 применены. Исходные данные сохранены, повторный `make seed` проверен. Регрессионные проверки восстановления выполнены на отдельной временной PostgreSQL. Подробности — в [разборе миграций](project-walkthrough.md#7-миграции-и-исправление-ошибки).

## JWT и cookie — следующий этап

Браузер может передавать JWT в HttpOnly cookie с Secure и подходящим SameSite. Сервер проверяет подпись, допустимый алгоритм, issuer, audience и срок, затем формирует identity. Для cookie-авторизации изменяющие запросы защищаем от CSRF. Выбор кабинета в UI следует правам, но сервер проверяет права независимо от UI.

Отдельной cookie role нельзя доверять. Подписанный claim роли также не заменяет проверку доступа к конкретному организатору. Покупатель может быть одновременно организатором; роль не делит профили навсегда. [JWT best practices](https://www.rfc-editor.org/rfc/rfc8725.html), [OWASP Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html).

## Как реализуем QR

После подтверждённой оплаты выдаём уникальный случайный токен достаточной длины. QR-библиотека кодирует его в PNG. В PostgreSQL сохраняем hash токена и состояние билета, приватный QR-файл хранится в S3. Пользователь получает изображение только после проверки владельца билета.

Контролёр сканирует изображение телефоном. Его клиент отправляет токен в POST /admission/check-ins. Сервер проверяет права контролёра на сеанс, находит билет по hash и атомарно меняет active на used. Повторный запрос не разрешает второй вход. Само открытие картинки или GET-запрос не погашает билет. QR не содержит персональные данные или JWT учётной записи.

Выдача файла, повторы задания, сбой загрузки в S3 и ограничения времени входа войдут в отдельное ТЗ фичи tickets. Сейчас добавлены только поля модели.
