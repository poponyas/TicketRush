## 1. Общий пример

Анна работает у организатора «Go Community». Организатор создаёт мероприятие «Go Live». Оно проходит 15 и 16 ноября в конференц-зале. На каждый день продаются обычные и VIP-билеты. Иван удерживает два обычных билета на 15 ноября, оплачивает их и получает два QR-билета.

```text
Organizer «Go Community»
  └── Event «Go Live»
      ├── Session 15 ноября, 18:00
      │   ├── TicketType «Обычный»: 20 билетов по 1000 RUB
      │   └── TicketType «VIP»: 5 билетов по 3000 RUB
      └── Session 16 ноября, 18:00
          ├── TicketType «Обычный»: другой остаток
          └── TicketType «VIP»: другой остаток

Иван → Booking на 15 ноября
         └── BookingItem: 2 обычных билета по 1000 RUB

Order: 2000 RUB, ссылается на Booking
  ├── Payment: попытка оплаты
  ├── Ticket №1
  └── Ticket №2
```

Event отвечает на вопрос «что за мероприятие», Session — «когда и где», TicketType — «какой тариф, цена и остаток». Booking — «что временно удержали», Order — «какую покупку оформляем», Payment — «что происходит с оплатой», Ticket — «с каким правом человек входит».

## 2. Что готово сейчас

`internal/core/domain` описывает понятия продукта. Поля вроде `Session.EventID` и `TicketType.SessionID` — ссылки по UUID, а не вложенные копии других объектов. Реализация операции решает, какие связанные записи надо прочитать.

Структура в Go ещё не означает, что уже есть таблица, CRUD или работающий процесс. Сейчас готов CreateEvent, схема каталога и локальная dev identity. Покупка, оплата, выдача QR, проверка входа, Kafka и JWT/OIDC ещё не реализованы.

| Модель | Состояние хранения после 003 |
|---|---|
| User, Organizer, OrganizerMembership | Таблицы уже есть |
| Event, Venue, Session, TicketType | Таблицы уже есть; готов только CreateEvent |
| Money | Значение внутри других моделей, отдельной таблицы нет |
| Role | Тип с константами; роль членства хранится в organizer_memberships |
| Booking, BookingItem | Новые типы в Go; старая bookings в БД пока имеет учебный формат |
| Order, Payment, Ticket | Типы будущих фич; таблиц пока нет |
| OutboxEvent, IdempotencyRecord | Типы будущей надёжной обработки; таблиц пока нет |

Сейчас `Validate()` есть у Event, Money и TicketType. Остальные модели — основа полей и статусов. Их методы и правила добавим вместе с соответствующей фичей.

Domain описывает приложение, DTO — формат общения с клиентом. Например, внутреннее `Title` становится JSON-полем `name`. Доменные модели не нужно напрямую отдавать во всех HTTP-ответах.

## 3. Каждая сущность domain

### User — user.go

Пользователь сервиса. И Анна, и Иван — User.

`ID` — внутренний UUID, `Email` и `DisplayName` — профиль. `Issuer` обозначает внешнего провайдера входа, `Subject` — аккаунт у него. У разных провайдеров одинаковый Subject может обозначать разных людей, поэтому важна пара Issuer/Subject. `CreatedAt` — время создания профиля у нас.

Один человек может покупать билеты и работать организатором одновременно. Два отдельных аккаунта для этого не нужны.

### Role — role.go

Именованный строковый тип с константами buyer, organizer, controller, admin. Помогает избежать случайных опечаток и обозначить допустимые роли.

Buyer покупает; organizer управляет своими мероприятиями; controller проверяет вход; admin относится к будущим административным функциям. Наличие констант ещё не означает реализацию всех этих возможностей.

Роль устанавливает сервер. Cookie `role=organizer` сама по себе не даёт прав. И даже роль organizer не даёт доступ к мероприятиям всех организаций.

### Organizer — organizer.go

Организация или команда, владеющая мероприятиями. В примере это «Go Community». Поля: ID, название Name и CreatedAt.

У одного организатора может быть несколько сотрудников. Поэтому Organizer и User — разные модели: организация не равна одному человеку.

### OrganizerMembership — organizer_membership.go

Связь пользователя с организацией и его ролью внутри неё:

```text
OrganizerID = Go Community
UserID = Анна
Role = organizer
```

У другой организации Анна может иметь другие права. Второй пользователь у Go Community может иметь роль controller.

В текущей таблице одна запись и одна роль на пару OrganizerID/UserID. Несколько ролей на одно членство потребуют расширения. CreateEvent проверяет членство organizer именно в нужной организации.

### Event — event.go

Карточка мероприятия: название, описание, категория, афиша и владелец.

- OrganizerID — владелец.
- Title, Description, Category — описание.
- PosterKey — ключ афиши в хранилище, а не байты изображения.
- Status — draft, published, archived.
- CreatedAt, UpdatedAt — время создания и изменения карточки.

NewEvent создаёт UUID, обрезает пробелы по краям текстов и задаёт draft. Validate проверяет IDs, непустое название до 200 символов, описание до 10000, категорию до 100 и допустимый статус.

Время в конструкторе не заполняется: его возвращает PostgreSQL через INSERT RETURNING. Это единый источник времени создания.

Цены и количества билетов здесь нет: для разных дат и тарифов они могут различаться. Публикацию и её требования ещё будем реализовывать.

### Venue — venue.go

Физическая площадка: Name, City, Address, Timezone. Например, конференц-зал в Москве с Timezone `Europe/Moscow`.

На одной площадке может проходить много сеансов разных мероприятий. Timezone нужен для отображения локального времени. В PostgreSQL timestamptz хранит момент времени; название часового пояса для отображения лежит отдельно в Venue.

CreatedAt — время создания записи площадки, а не начало мероприятия.

### Session — session.go

Одно конкретное проведение Event: 15 ноября в определённом зале.

EventID и VenueID связывают его с карточкой и площадкой. StartsAt/EndsAt — время проведения, SalesStartAt/SalesEndAt — окно продаж. Статусы: draft, scheduled, cancelled, completed.

В SQL уже есть проверки: окно продаж положительное, продажи заканчиваются не позже начала, заданное окончание позже начала. Go-валидацию и права допишем с Session CRUD.

EndsAt имеет тип `*time.Time`: nil означает, что окончание не задано. Указатели такого вида позволяют явно представить необязательное значение.

### Money — money.go

Сумма с валютой. Это тип значения: собственного ID у него нет.

```go
price, err := domain.NewMoney("1000.50", domain.CurrencyRUB)
```

Amount использует decimal.Decimal и выражает рубли. Currency пока только RUB. NewMoney разбирает строку и проверяет сумму: неотрицательная, без дробной копейки, в диапазоне NUMERIC(18,2). Ограничены длина записи и экспонента, чтобы не запускать огромные вычисления на произвольном вводе.

Для арифметики используй Add/Mul, не переводя цену в float64. В JSON сумма — строка. Незначащие нули могут исчезнуть: `"1000.50"` и `"1000.5"` означают одну стоимость. Отображение ровно двух знаков — задача интерфейса.

Ноль допустим для бесплатного тарифа. Правила округления комиссий и распределения суммы decimal сам не выбирает — их определим в платёжной фиче.

### TicketType — ticket_type.go

Тариф одного Session: обычный или VIP. Он описывает множество билетов одного вида.

Price — стоимость одного билета. Capacity — весь объём, Available — свободно, Held — удержано неоплаченными бронями, Sold — оплачено.

```text
available + held + sold = capacity

Начало:             20 + 0 + 0 = 20
Удержали два:       18 + 2 + 0 = 20
Оплатили эти два:   18 + 0 + 2 = 20
```

Если бронь истекла до оплаты, состояние вернётся к 20 + 0 + 0. Изменения счётчиков должны выполняться согласованно в транзакции; это часть будущей booking-фичи.

Validate проверяет IDs, название, положительную capacity, неотрицательные счётчики, их согласованность и цену. Основные ограничения продублированы в БД.

TicketType — тариф, Ticket — выданное конкретное право входа.

### Booking — booking.go

Временное удержание билетов для покупателя. Иван выбрал два билета, но ещё не оплатил.

UserID указывает на покупателя, SessionID — на дату, ExpiresAt — на срок удержания. Состав хранится отдельно в BookingItem, поэтому общего Quantity в Booking нет.

Планируемые переходы: held → confirmed при оплате, held → cancelled при отмене, held → expired при истечении. Только отмена/истечение действующего held возвращает остаток. Повтор действия не возвращает билеты второй раз.

Возврат уже оплаченной покупки — отдельный процесс.

### BookingItem — booking_item.go

Строка состава брони: например, два обычных билета по 1000 RUB.

BookingID — родительская бронь, TicketTypeID — тариф, Quantity — количество, UnitPrice — зафиксированная цена одного билета.

Если организатор завтра повысит цену, эта строка останется по прежней стоимости. Для начала поддерживаем один тариф в броне; структура оставляет возможность расширения.

### Order — order.go

Оформляемая покупка с итоговой суммой. Связан с Booking и User. Total фиксирует сумму, PaidAt появляется после подтверждения оплаты.

Статусы: pending, paid, cancelled, refund_required, refunded. Booking отвечает за краткосрочное удержание и остатки, Order — за результат покупки и её историю.

RefundRequired пригодится, если деньги пришли после освобождения брони. Нельзя подтвердить такой заказ за счёт билетов, уже проданных следующему покупателю.

### Payment — payment.go

Попытка оплаты заказа. Один Order может пережить несколько попыток.

Provider обозначает платёжный компонент, ProviderPaymentID — идентификатор операции у него. IdempotencyKey защищает повтор создания платежа. Amount должна совпадать с ожидаемой суммой заказа. Статусы: pending, succeeded, failed, refunded.

Провайдер сообщает результат, а наше приложение проверяет его и выполняет допустимый переход заказа. Перенаправление браузера на страницу «успешно» не является подтверждением платежа.

Данные банковской карты в Payment не храним.

### Ticket — ticket.go

Один выданный билет. За два оплаченных билета Иван получит два Ticket с разными кодами.

OrderID/UserID/SessionID/TicketTypeID связывают его с покупкой и сеансом. Status — active, used, revoked. UsedAt — время прохода, CheckedInBy — кто подтвердил вход.

TokenHash — hash случайного QR-токена. QRObjectKey — ключ приватного изображения в S3. `json:"-"` исключает эти поля из обычной JSON-сериализации. Публичный ответ всё равно будем собирать через DTO.

Из hash нельзя восстановить исходный токен. QR-файл поэтому сохраняется при выдаче. Надёжную выдачу, повтор задания и сбой S3 будем проектировать в отдельном ТЗ.

Контролёр отправляет считанный токен серверу. Сервер проверяет права и билет, затем атомарно меняет active на used. Открытие картинки не погашает билет. Выдача QR и check-in сейчас ещё не реализованы.

### OutboxEvent — outbox_event.go

Служебная запись о событии для последующей публикации. Например, OrderPaid.

ID — стабильный идентификатор для распознавания повторов. AggregateID — ID объекта, например заказа. Type/SchemaVersion — название и версия формата, Payload — JSON события. PublishedAt/Attempts отражают отправку.

План: подтверждение заказа и запись outbox выполняются в одной SQL-транзакции. Worker позже отправляет событие в Kafka. При сбое Kafka запись остаётся и будет отправлена после восстановления. Повторы отправки допустимы, consumer должен распознавать ID события.

Это пока модель: таблицы outbox и worker ещё нет.

### IdempotencyRecord — idempotency_record.go

Запись для ответа на повтор команды клиента. Иван нажал «забронировать», ответ потерялся, клиент повторил запрос с тем же ключом — нужно вернуть прежнюю бронь.

Область ключа: UserID + Operation + Key. RequestHash отличает настоящий повтор от другого запроса с тем же ключом. HTTPStatus/Response сохраняют ответ, ExpiresAt — срок хранения.

IdempotencyRecord защищает входящие команды, OutboxEvent отвечает за доставку исходящих событий. Это разные части работы с повторами.

## 4. Путь запроса CreateEvent

```http
POST /api/v1/organizer/events
Content-Type: application/json

{"name":" Go Live ","description":"Конференция","category":"conference"}
```

### Роутер и middleware

В main маршрут связан с хендлером. Middleware создают RequestID, добавляют логгер запроса в context и, если явно включён dev-режим, серверную identity.

RequireOrganizer проверяет identity и роль: отсутствие identity — 401, неподходящая роль — 403. SQL дополнительно проверит членство конкретного организатора.

### transport/create_event.go

Хендлер берёт r.Context(), identity и логгер. Проверяет Content-Type, ограничивает тело 1 MiB, разбирает его в EventCreateRequest. Неизвестные поля и несколько JSON-значений отклоняются.

OrganizerID/UserID берутся из серверного контекста. Назначить себе чужого организатора или published через JSON нельзя. Затем создаётся CreateEventInput и вызывается EventsService.

Хендлер занимается HTTP, а не SQL.

### service/create_event.go

Сервис проверяет UserID, создаёт Event через NewEvent, вызывает Validate и передаёт модель репозиторию.

На этом этапе пробелы удалены, UUID сгенерирован, статус draft, CreatedAt ещё нулевой. В сервисе нет ResponseWriter или HTTP DTO.

### repository/save_event.go

Репозиторий ставит таймаут SQL и выполняет параметризованный INSERT SELECT. Аргументы передаются отдельно как $1…$7.

SELECT ищет членство organizer для UserID/OrganizerID. Если его нет, INSERT не получает строки и ничего не создаёт. QueryRow.Scan возвращает ErrNoRows, который преобразуется в ErrForbidden.

При успехе RETURNING возвращает созданные поля и время из PostgreSQL. Scan заполняет domain.Event. Внутренние ошибки оборачиваются через %w, сохраняя причину.

### Обратный путь

Repository возвращает Event → service возвращает Event → transport преобразует в EventResponse.

Общий response-handler сначала сериализует ответ, затем отправляет заголовки и статус. Успех — 201 Created, application/json, Location на будущую ручку `/api/v1/organizer/events/{id}`.

При внутренней ошибке детали остаются в логах, клиент получает безопасные code/message/request_id. GET по Location ещё предстоит написать.

## 5. Как работают интерфейсы

В service/service.go EventsRepository описывает нужное сервису поведение. Сервис хранит поле этого интерфейсного типа. В transport/transport.go EventsService описывает поведение, нужное хендлеру.

Конкретные структуры с подходящими методами автоматически удовлетворяют интерфейсам. Никакого implements нет.

```text
pool
 → repository.NewEventsRepo(pool)           конкретный SQL-репозиторий
 → service.NewEventsService(repository)    хранит репозиторий как интерфейс
 → transport.NewEventsHTTPTransport(service)
 → роутер вызывает CreateEvent
```

Во время выполнения внутри интерфейса находится конкретная реализация. В тесте это может быть заглушка, в приложении — PostgreSQL-репозиторий. Поэтому сервис можно тестировать без базы.

Интерфейс не делает вызов удалённым и не создаёт микросервис. Это обычный Go-вызов в том же процессе.

В таблице core означает `internal/core`.

godotenv загружает .env в окружение процесса, не заменяя уже заданные переменные. envconfig затем читает окружение и преобразует строки в типы. Отсутствие .env допустимо, если нужные переменные уже заданы.

OpTimeout не применяется автоматически ко всем запросам. Репозиторий создаёт context.WithTimeout и передаёт его pgx. Пул создаётся один раз, не на каждый HTTP-запрос.

В main ресурсы закрываются при возврате из run. Сигнал запускает Shutdown с отдельным таймаутом. При ошибке конфигурации или подключения сервер не запускается.

DevIdentity работает только на loopback при DEV_AUTH_ENABLED=true. JWT она не проверяет: это временный Postman-режим. Без dev identity и до реализации настоящей авторизации ручка отвечает 401.

With создаёт дочерний логгер с полями запроса, но файл закрывает только корневой Logger. FromContext без логгера возвращает no-op: паники нет, записей тоже нет. В штатных HTTP-запросах main заранее добавляет реальный логгер.

## 7. Миграции и исправление ошибки

### Причина присланного сбоя

events/bookings были созданы вручную. migrate не знал об этом и попытался выполнить 001. CREATE TABLE events завершился ошибкой, а в schema_migrations остались version=1, dirty=true.

Dirty означает незавершённый шаг в журнале миграций, а не автоматически испорченные бизнес-данные. migrate блокирует движение, пока схема и версия не согласованы. Down не предназначен для очистки такого состояния. [Объяснение migrate](https://github.com/golang-migrate/migrate/blob/master/FAQ.md#what-does-dirty-database-mean).

### scripts/migration_prepare.sql

Перед migrate-up создаются временные эталонные таблицы 001. Сравниваются столбцы, типы, nullability, defaults, ограничения и индексы. Затем эталон расширяется ограничением 002 и проверяется этот вариант.

Если первоначальная ручная схема точно совпала, меняется только журнал: версия становится 1 или 2, dirty=false. Строки events/bookings не изменяются. Далее migrate выполняет оставшиеся шаги.

Неизвестная/неполная схема, дополнительные таблицы или dirty более поздней версии приводят к отказу. Автоматическая подготовка не скрывает произвольные ошибки миграций.

На чистой отслеживаемой базе ремонт не выполняется. На пустой migrate создаёт всё обычным способом. Временные эталоны исчезают при завершении транзакции/сессии.

Локальная база после исправления: version=3, dirty=false. Первоначальное событие сохранено, повторный seed не создаёт дубликаты.

### Файлы

| Файл | Действие |
|---|---|
| 001_init.up.sql | Первоначальная учебная схема events/bookings |
| 001_init.down.sql | Удаление этой схемы и данных при явном откате |
| 002.up.sql | Ограничение названия до 200 символов |
| 002.down.sql | Удаление ограничения |
| 003_catalog.up.sql | Новая карточка, users, organizers, membership, venues, sessions, ticket_types |
| 003_catalog.down.sql | Откат каталога; отказ, если новым карточкам пришлось бы придумывать старые остатки |
| scripts/seed.sql | Локальные fixtures; ON CONFLICT не перезаписывает существующие записи |
| scripts/migration_prepare.sql | Проверенный переход первоначальной ручной схемы на журнал migrate |

В 003 старые события получают специального legacy-организатора и draft. Старые остатки сохраняются, новая Go-модель их не использует. Старым данным не придумываются дата проведения и цена.

Если событие с фиксированным ID seed уже было, seed не меняет его владельца. Поэтому dev-организатор не получает автоматически старое legacy-событие. Для следующих CRUD используй ID, возвращённый новым POST.

### Команды

```sh
make seed             # база → подготовка журнала → миграции → fixtures
make migrate-version  # текущая версия
make run              # успешный seed → Go-сервер
make migrate-down     # намеренный откат последней миграции
```

Make прекращает выполнение при ошибке зависимости. Make run не запустит приложение после провала seed. Если отдельно написать make seed и следующей строкой go run, оболочка может выполнить вторую команду независимо от первой.

Down меняет схему и может удалять данные согласно down-файлу. Повторное применение проверяем через up, а не циклом down/up на рабочей базе.

## 8. Что читать для следующего CRUD

Для GET карточки организатора:

1. domain/event.go — что возвращаем.
2. transport/dto_event.go — поля ответа клиенту.
3. service/service.go — требуемый метод репозитория.
4. repository — SQL с проверкой владельца и отсутствующей строки.
5. service — правила и вызов репозитория.
6. transport — UUID из URL, context, сервис, DTO и ответ.
7. main — маршрут.
8. HTTP- и SQL-тесты.

Цель: GET /api/v1/organizer/events/{id} для своей карточки, включая draft. Публичная GET /api/v1/events/{id} позже покажет только published.

Для Event CRUD сейчас достаточно Event, Identity и OrganizerMembership. Order, Payment, Ticket и Outbox помогают понять будущую покупку, но не требуют немедленной реализации.
