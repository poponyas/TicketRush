# Интерфейс TicketRush

## Запуск

Из корня проекта: `make run`, затем открыть **http://127.0.0.1:8080**. В другом терминале — `make analytics`, чтобы обновлялись отчёты.

Node.js, npm и отдельный frontend-сервер для запуска не нужны. `web/embed.go` встраивает HTML, CSS, JavaScript и SVG в Go-бинарник через `go:embed`. После изменения этих файлов **перезапусти API**: запущенный бинарник хранит предыдущую версию.

Используй обычную JWT-аутентификацию (`DEV_AUTH_ENABLED=false`). Для подтверждения брони нужен `MOCK_PAYMENTS_ENABLED=true`. Все платежи имитируются, банковские данные не запрашиваются.

## Что можно делать

- Афиша: настоящие опубликованные мероприятия, поиск и категории на текущей странице, пагинация.
- Мероприятие: описание, площадка, выбор сеанса, тарифа и количества мест, реальные цены и остатки.
- Аккаунт: регистрация, вход, автоматическое обновление access token, серверный logout.
- Покупатель: свои брони всех статусов, время удержания, отмена, demo-подтверждение, билеты, просмотр и скачивание QR.
- Организатор: выбор своей организации, создание/изменение/удаление черновика, сеансы и тарифы, публикация сеанса и мероприятия, загрузка афиши, аналитика за период.
- Владелец площадки: отдельное право создавать площадки; каталог площадок доступен всем.
- Контролёр: выбор опубликованного мероприятия своей организации, сеанса и проверка кода билета. Для demo код можно скопировать из окна QR покупателя. Камера и распознавание QR в этой версии не реализованы.

Самостоятельной выдачи ролей в интерфейсе нет: новый пользователь — покупатель. Права организатора, контролёра и владельца площадки задаются в базе существующими механизмами backend. Demo-аккаунты перечислены в основном README.

## Порядок чтения файлов

| Файл | За что отвечает |
|---|---|
| `embed.go` | Раздача встроенных файлов, запрет списка каталогов, CSP и заголовки безопасности. |
| `static/index.html` | Общая оболочка: header, навигация, main, footer, уведомления. |
| `static/styles.css` | Цвета, компоненты, макеты, адаптация к телефону, focus и reduced motion. |
| `static/app.js` | Маршруты в URL после `#`, текущий профиль, вход/выход в шапке, очистка таймеров и QR blob URL при смене страницы. |
| `static/api.js` | Единственная точка HTTP-запросов: bearer, X-Organizer-ID, JSON/файл/blob, timeout, ошибки, единичный refresh для параллельных запросов. |
| `static/ui.js` | Экранирование текста, иконки, даты, цены, формы, диалоги, пагинация и уведомления. |
| `static/views/catalog.js` | Афиша, карточка мероприятия, выбор сеанса/тарифа и создание брони. |
| `static/views/account.js` | Регистрация/вход, кабинет, QR и подтверждение/отмена брони. |
| `static/views/workspace.js` | Организация, CRUD черновика, сеансы, тарифы, публикация, афиша, отчёт, площадки и контроль входа. |
| `static/assets/` | Локальная SVG-афиша для мероприятий без изображения и favicon. Никаких внешних CDN. |
| `tests/api.test.mjs` | Проверки refresh, logout, отсутствия повторной отправки неопределённого POST, rate limit и точного отображения денег. |

Обработчик `/` возвращает HTML, `/app/*` — статические файлы, а все данные идут через существующий `/api/v1/*`. Hash-маршрутизация позволяет открывать ссылки вроде `/#/account` без fallback для неизвестных API-методов. Отдельный CORS не требуется: API и фронтенд имеют один origin.

## Два новых API-метода

`GET /api/v1/me` возвращает свой ID, email, имя, флаг владельца площадки и организации с ролями. Это позволяет выбрать организацию из списка, а не вводить UUID вручную.

`GET /api/v1/me/bookings?limit=20&offset=0` возвращает только брони пользователя из проверенного context, с названием события, площадкой, датой, количеством и суммой **из booking_item**. Текущая цена тарифа не влияет на историю покупки. Пользовательский `user_id` из query не используется.

Оба метода находятся в `internal/feature/account/`: `models.go` — модели чтения, `repository/` — SQL, `service/` — проверки и пагинация, `transport/` — HTTP/identity. Ответы имеют `Cache-Control: private, no-store`. Пароли и токены в профиль не входят. Эти модели чтения не меняют сущности бронирования и их жизненный цикл.

## Как проходит покупка

1. Каталог запрашивает опубликованные мероприятия. Карточки дополнительно показывают ближайший возвращённый сеанс, площадку и минимальную доступную цену этого сеанса.
2. Страница мероприятия загружает сеансы и тарифы. Клиентская проверка дат и остатков помогает пользователю; окончательное решение принимает транзакция backend.
3. Создание брони возвращает ID. Интерфейс открывает отдельную страницу брони и получает её актуальный состав из API.
4. Обратный отсчёт показывает время до `expires_at`. Он не освобождает билеты: это делает backend worker. При истечении интерфейс повторно читает статус и отключает подтверждение.
5. Demo-confirmation переводит на список билетов. Для QR выполняется авторизованный запрос PNG, создаётся временный blob URL; при закрытии окна или смене страницы URL освобождается.
6. Контроль входа отправляет подписанный код на backend. Повторный проход получает 409 и понятное сообщение.

При сетевой ошибке создания брони запрос автоматически не повторяется: перед повтором нужно посмотреть «Мои брони». Повтор подтверждения остаётся идемпотентным на backend.

## Аутентификация и ограничения

Существующий API выдаёт токены в JSON. Access token хранится в памяти страницы; refresh token — в `sessionStorage`, отдельно для вкладки. После перезагрузки страницы клиент обновляет токены и запрашивает `/me`. Параллельные запросы используют один refresh, чтобы не конкурировать при ротации. После logout запоздавший refresh не восстанавливает сессию.

Это практический вариант для текущего локального MVP. `sessionStorage` доступен JavaScript этого origin и не защищает от XSS как HttpOnly cookie. Для публичного развёртывания стоит отдельно переработать browser-auth на HttpOnly/Secure cookies с защитой CSRF или BFF. Сейчас динамический текст экранируется, скрипты и ресурсы локальные, CSP запрещает inline-скрипты и внешние источники. Токены не попадают в URL, логи и HTML.

Наличие кнопки или сохранённый профиль не дают доступа: backend проверяет JWT, действительность auth-сессии, членство и состояние сущности при запросе. Не используются роли из localStorage или неподписанных cookie.

Цены API приходят десятичными строками. Для сумм и умножения на количество используются целые копейки `BigInt`, для форматирования — `Intl`, без потери копеек на больших значениях. Числа отправляются как строки в `Money.amount`.

Поиск фильтрует текущую страницу афиши, это подписано в интерфейсе. Формы выбора площадки/сеанса/тарифов загружают первые 100 записей; для большого каталога нужны отдельные поисковые API и пагинация этих селекторов. Опубликованное описание и время не редактируются: текущий backend разрешает это только черновикам.

## Проверки

- `make test-web` — 6 JavaScript-проверок без npm-пакетов; нужен Node.js 22+ только для тестов.
- `make test-integration` — отдельная PostgreSQL, проверки изоляции аккаунтов, цены-снимка, ролей и пагинации, все Go-тесты с race detector.
- `go test ./web` — встроенные ресурсы, типы содержимого, отсутствие доступа к `.env`/каталогам, CSP.
- `python3 scripts/smoke.py` — существующий HTTP-сценарий при запущенных API и consumer.

Ручной UI smoke: зарегистрировать покупателя → выбрать сеанс/тариф → забронировать → подтвердить → показать QR → обновить страницу → проверить сохранение входа. Затем выйти, войти организатором → создать черновик → сеанс → тариф → открыть продажи сеанса → опубликовать мероприятие. Для контроля входа использовать отдельный тестовый билет: первый проход успешен, повтор отклоняется.
